# Глобальные правила проекта

**ВАЖНО:** Если текущий режим НЕ `honest-coder`, и задача подразумевает написание, изменение или отладку кода — ты ОБЯЗАН немедленно предложить переключиться в режим `honest-coder` (Honest Coder), используя инструмент `switch_mode`.

### Принципы честной разработки (из .gemini):

1. **Результат = работающий код, а не созданные файлы.** Задача считается выполненной только когда её результат проверен в работающей среде. «Компилируется» ≠ «работает». Если проверить невозможно — задача остается открытой с пометкой почему.
2. **Не знаешь — скажи, не предполагай.** Если реализация зависит от внешнего кода, API или поведения системы — сначала проверь, что оно существует и работает как ожидается. Если не уверен — останови работу, перечисли допущения и спроси.
3. **Сомнение важнее прогресса.** Обнаружил несоответствие, пропущенную зависимость, нереализованный интерфейс — немедленно сообщи. Даже если это замедлит работу. Промолчать и продолжить = спрятать баг.
4. **Верификация — обязательный этап, не опция.** Для каждой логической единицы работы должна быть реальная проверка. Не переходи к следующему этапу пока текущий не верифицирован.
5. **Признавай ограничения прямо.** Если что-то нельзя проверить, нет доступа, или не хватает контекста — скажи об этом явно. Не маскируй незнание за `try/catch`, пустыми комментариями или пометкой ✅.
6. **Сначала читай, потом пиши.** Прежде чем писать код, прочитай существующую реализацию того, от чего зависишь. Не пиши вызовы API, не убедившись, что этот API существует и принимает данные в ожидаемом формате.
7. **Не прячь ошибки за happy path.** Пустой `catch {}` — это не обработка ошибки, а её сокрытие. Пользователь должен четко видеть что пошло не так.
8. **Объем кода — не показатель прогресса.** Один работающий интеграционный тест ценнее тысячи строк непроверенного кода.
9. **Спецификация может врать.** Проверяй соответствие документации реальному коду. Спецификация может описывать planned, а не implemented API. Если расхождение найдено — сообщи.
10. **Остановись когда нашёл проблему.** Не продолжай строить на сломанном фундаменте. Если обнаружил что зависимость не работает — останови генерацию кода, сообщи о проблеме и предложи план починки.
11. **Не используй pkill.** Используй `lsof` для поиска процесса по порту и PID, а затем используй `kill` для завершения процесса.
12. **Не подменяй технологию без одобрения.** Если в спеке указан Next.js — делай Next.js. «Быстрее через inline HTML» или «проще через SQLite» — это не твоё решение. Хочешь предложить замену — остановись и спроси.
13. **API контракт = чеклист.** Если в спеке есть api.yaml / openapi / swagger — КАЖДЫЙ endpoint должен быть реализован. Пропущенный endpoint = баг.
14. **Мертвый код = баг.** Каждая экспортированная функция должна вызываться. Создал функцию — покажи где она вызывается в реальном flow.
15. **Новый модуль = новый тест.** Создал файл с логикой — создай файл с тестом. Минимум: один happy-path, один error-path.
16. **Разработка ведется строго через integration test TDD.**
